# ADR 0005: TypeScript 7 and type-aware Oxlint own the check gate

## Decision

The workspace compiles with **tsrs** `0.25.0-ts7.1.0-beta` — a Rust port of the TypeScript `7.1.0-beta` compiler — and lints with Oxlint `1.94.0` in type-aware mode, on the same compiler: `pnpm lint` is `effect-tsgo --tsrs-lint oxlint`, and `@effect/tsgo@0.70.0` supplies the patched Oxlint binding and the patched `tsrs` type-aware pass behind it. `prepare` patches only the compiler (`effect-tsgo patch --tsrs`), because the Oxlint side is preloaded per run rather than written into `node_modules`. Oxlint — not the compiler — is the only surface that reports Effect diagnostics: `packages/config/tsconfig.base.json` sets `diagnostics: false` on the language-service plugin and `oxlint.config.ts` extends `@effect/tsgo/oxlint-presets` `recommended` and `effect-native`. Every package declares `typecheck: tsrs --noEmit`, and `pnpm check` (`turbo run check`) runs those together with the type-aware lint pass and the formatter check. CI runs it as the `checks` job.

## Why

Nothing typechecked the workspace. There was no `typecheck` script in any package, no `typecheck` task in `turbo.json`, and no lint or typecheck step in CI: `apps/web` builds through Vite, `apps/server` through Rolldown, and neither reads types. `packages/domain` compounded this by declaring `composite`, `declaration`, and `outDir` with nothing to emit them, so its `exports` map pointed at source while a latent `TS7056` sat in `rpc-router.ts` waiting for the first tool that asked tsc to serialize a declaration. TypeScript was an editor feature, not a gate.

Turning it on is cheap now. All 26 packages typecheck clean under TypeScript 7, and the first run surfaced exactly three real problems: the `TS7056` above and two tsconfigs (`packages/sdk`, `packages/feedback-widget`) that declared `outDir`/`declaration` without `rootDir`. That is the whole migration.

Type-aware linting had been disabled deliberately — the config carried "revisit once Oxlint's tsgolint path can integrate with `@effect/tsgo` diagnostics" next to `typeAware: false`. That integration is what `@effect/tsgo` now is: it supplies an Oxlint build with the `effecttsgo` plugin wired in, and a type-aware linter behind it — `oxlint-tsgolint` when this ADR was written, `tsrs` since `0.70.0`. The cost of the old setting was 17 `typescript/*` rules switched off, including `no-floating-promises`, which is the highest-value rule in an async codebase.

Splitting responsibility between the two tools keeps each one honest. `tsc` owns types and stays fast enough to cache per package; Oxlint owns Effect rules, where per-rule severity, file-scoped overrides, and a single cached run are easier to reason about than a tsconfig severity map. Running the Effect rules in both places would report every finding twice.

## Consequences

Every Effect rule now lives in `oxlint.config.ts`, and changing a diagnostic severity is a config edit rather than a tsconfig edit. The `effecttsgo` rules that fire on usage anywhere in a file — `async-function`, `global-date`, `process-env`, `global-console` — are `off` with written reasons, because this repo deliberately keeps those behaviors outside Effect at its boundaries (Playwright specs, TanStack Start server functions, better-auth plugins, the standalone widget, Node scripts). Their `-in-effect` siblings stay on, and those are the ones that describe a defect.

`oxlint.config.ts` extends two `@effect/tsgo` presets, `recommended` and `effect-native`, and the second is not optional. `@effect/tsgo@0.46` moved twenty rules — every `global-*`, `crypto-*`, `process-env`, `new-promise`, `schema-sync` and `instance-of-schema` — out of `recommended` and into the opt-in `effect-native` preset. Extending only `recommended` therefore drops `global-date-in-effect`, the rule the paragraph below is about, without failing anything: the diagnostic simply stops being reported. The two presets together are exactly the rule set `0.45.0`'s `recommended` carried. A tsgo bump is not safe to review by watching `pnpm check` go green; it has to be reviewed by diffing the presets.

That distinction is the thing to know when reading the warning count. The bare variants fire in files with no Effect context at all, so their totals overstate the problem badly: `new-promise` (21) is Storybook mocks, a framework-agnostic editor, and Playwright specs; `global-timers` (12) is Storybook, the embeddable SDK, a PostHog provider, and a clipboard hook; `schema-sync` (39) is entirely `decodeUnknownSync` in test files, where a throw is what you want; `any-unknown-in-error-context` (517) is 431 test files plus HTTP router plumbing where the `unknown` is inference, not a decision. None of those should be churned to satisfy a rule whose advice does not apply. What is genuinely actionable, in order:

1. `global-date-in-effect` — cleared outside `packages/db/seed.ts`, and flipped from `warn` to `error` with a file-scoped `warn` override for that script. The rule ranked first because `new Date()` inside Effect bypasses `Clock`, so a service that does it cannot be tested against `TestClock`. The runtime services read `Clock`/`DateTime`, and the fixtures that constructed a `Date` inside Effect were converted: dynamic reads go through `DateTime.nowAsDate` or `Clock.currentTimeMillis`, and fixed instants go through a local `dateAt` helper that builds the `Date` with `DateTime`. The 22 left are the seed script's snapshot timestamps; that script is a human-facing CLI, so deciding them is separate work rather than a mechanical sweep.
2. `typescript/no-floating-promises` (49, 45 of them production, mostly React event handlers) — a floating promise in a handler is an unhandled rejection.
3. `strict-effect-provide` (31) and `any-unknown-in-error-context` (the 86 production sites) — both now `error` and clear. The second cleared itself once the `effect` bump was actually read: the 154 findings that survived the tsgo upgrade were every one of them downstream of a single breakage — Effect `4.0.5` turned `Crypto.randomUUIDv4`/`randomUUIDv7` from properties into methods, so `crypto.randomUUIDv4.pipe(...)` became `.pipe` on a function, the whole Effect became `unknown` in both channels, and the diagnostic followed that `unknown` outward to every repository and handler that consumed one. Twelve call sites gained their parentheses and 154 warnings went with them. That is the rule working as intended, and it is why the count is worth reading rather than estimating.
4. `global-console-in-effect` (26) is 24/26 in `packages/db/seed.ts`, a human-facing CLI where `console.log` prints the output an operator expects; `Effect.log` would add fiber and timestamp noise. Leave it unless that script becomes machine-read.

Each should be fixed and then flipped to `error`. None should be silenced.

One rule is `off` for a reason that is neither "the code does this legitimately" nor "the advice does not apply": `unstable-api-usage`, which `@effect/tsgo@0.47` enables by default and which reports 928 findings here. Effect 4.0 moved `http`, `http-api`, `rpc`, `sql`, `persistence`, `reactivity` and `workflow` from `effect/unstable/*` to `effect/*` while keeping every one of them tagged `@stability unstable`, so the rule fires on the imports this server is built out of and there is nothing stable to migrate to. The warning is a true statement about the dependency and not about this code, and the control for it is the catalog pin, which is what decides when those APIs move. Leaving 928 of them as warnings would only train reviewers to skim the report, so the rule is off rather than ratcheted.

Tests keep one documented exception to the manual-runtime ban: `packages/auth/src/api-key.test.ts` builds `ManagedRuntime` values at module scope, because it shares one PGlite database across the file and passes it to the better-auth adapter as a plain value rather than inside an Effect. Its `oxlint-disable` carries the reason inline. Every other test file uses `it.effect`/`it.layer`, enforced by `tools/oxlint/effect-tests`.

`extends-native-error` stays on as a warning rather than being fixed: `RpcError` in `packages/web-shared` and `EmbedError` in `packages/sdk` are deliberately plain `Error` subclasses that never enter an Effect failure channel, and the SDK one must not pull `effect/Schema` into the embeddable bundle.

A dependency bump now has a version contract. `@effect/tsgo` names the compiler and Oxlint versions it supports, and `effect-tsgo --tsrs-lint oxlint` validates the installed pair on every lint run and refuses a mismatch, so these pins move together or not at all. It is also coupled to `effect` itself, which the patch command cannot check: the rules match on Effect's module paths, so `@effect/tsgo@0.45` keyed off `effect/unstable/*` reports nothing once Effect 4.0 drops the `unstable` segment. That failure is silent, so a tsgo bump is reviewed by diffing its presets against the ones the config extends, not by watching the gate.

The `0.47.2` → `0.56.0` bump is the first to exercise that contract concretely, and it dragged the other three pins with it: `0.56.0` supports TypeScript `7.0.2`, Oxlint `1.87`–`1.89` and `oxlint-tsgolint` `7.0.2003`/`7.0.2004`, so Oxlint and `@oxlint/plugins` moved to `1.89.0` and `oxlint-tsgolint` to `7.0.2004`, because those were the only installable versions left. Diffing the presets showed ten additions, no removals and no severity changes: seven in `recommended` (`effect-sleep-zero-to-yield-now`, `error-payload-shadows-name`, `experimental-api-usage`, `flat-map-to-tap`, `schema-class-missing-brand`, `schema-class-object-literal`, `unstable-api-usage`) and three in `effect-native` (`prefer-effect-array`, `prefer-effect-record`, `prefer-effect-string`). `unstable-api-usage` arriving in `recommended` is already covered by the `off` entry above; the rest were decided one at a time, with the reasoning beside their entries in `oxlint.config.ts`. Two account for 2,641 of the 2,651 new findings — the `prefer-effect-*` trio (2,514) and `schema-class-missing-brand` (127) — and both are `off` rather than ratcheted. The first is a stylistic swap to a module whose functions behave identically, at roughly a thousand sites that sit in browser bundles, Playwright specs and the published SDK, where the import is bundle weight and the behaviour is unchanged; the second fires only on `Schema.TaggedError`, whose required unique `_tag` already rejects two structurally identical errors, so the brand would be a symbol nothing matches on. `typescript/no-generated-empty-object-type` reports two findings, both a deliberate `Schema.Struct({})` that states "nothing to configure", and is `error` everywhere except those two named files.

The bump also showed what a green gate does _not_ prove. `typecheck` is cached, and the cache did not include the resolved dependency versions: appending a line to `pnpm-lock.yaml` left every package replaying `cache hit`, so after a real dependency bump a package whose types no longer compiled could report success from a run that predates the install. That is the hazard the `//#toolchain` and `//#knip` tasks document for themselves and dodge by not caching at all; `typecheck` is worth caching, so `turbo.json` names `pnpm-lock.yaml` as a `globalDependencies` entry instead — one miss per dependency change, and the cache still works for source-only edits. Two consequences for anyone bumping a train: read the result of `pnpm check --force` once, and treat a per-package `typecheck: cache hit` after an install as no evidence.

The `0.56.0` → `0.59.0` bump is where the compiler changed hands, and it is the cleanest exercise of the contract so far. `0.56.0` patched the Go compiler inside the `typescript` package; `0.59.0` adds `patch --tsrs`, so `prepare` patches the Rust compiler instead (`effect-tsgo patch --tsrs --oxlint`) and every `typecheck` script calls `tsrs`. The presets did not move at all — `0.56.0` and `0.59.0` ship byte-identical `oxlint-presets` and an identical Oxlint schema — so the bump added no rule, removed none and changed no severity. The four-pin train moved only because `0.59.0` is the release that supports tsrs `0.20.0-ts7.1.0-beta`, with Oxlint `1.87`–`1.89` and `oxlint-tsgolint` `7.0.2004`/`7.0.2005`; the workspace pins `1.89.0` and `7.0.2005`, which is where that pair sits today.

What did move is the checker: tsrs ports TypeScript `7.1.0-beta`, not `7.0.2`, and `7.1` reports three things `7.0.2` did not. All three are defects the older compiler could not see, and each was verified against `typescript@7.1.0-beta` before being treated as a tsrs finding — a Rust port that disagrees with its pinned Go source is a port bug, not a code bug, and the two need opposite responses.

1. `TS2883` in `packages/rpc-client`: the inferred type of the `Rpc` class cannot be named without a reference to `LegidError` from `../../domain/node_modules/@feeblo/id/src`, which only matters for a package that emits declarations. `rpc-client` declared `declaration`, `declarationMap`, `sourceMap`, `outDir` and `composite` and emits nothing — its `exports` map points at `./src/index.ts` and no script builds it — so the fix is the one this ADR already applied to `packages/domain`: the dead emit config is gone, and the diagnostic with it.
2. `DbClient.collection` in `@tanstack/db` resolves its overload from the descriptor. Under `7.1` the schema-taking overload also matches a schema-less descriptor, so `T` is inferred as `never` and every live query built from a materialized collection reads `never` rows — 747 errors in `apps/web` and 182 in `apps/public-feature-board`, every one of them downstream of that single call. Both apps now materialize through a local `materialize(client, descriptor)` helper that names the descriptor's three type arguments and therefore selects the schema-less overload. This is a workaround for an upstream inference regression, not a design change; when `@tanstack/db` fixes it, the helper is a no-op that can be deleted.
3. The same `never` collapse surfaced in `applyPublicCollectionIndexes`, where `createIndex((row) => row.postId)` reads a property of `never`; the same helper fixes it.

Nothing about the swap changes the split this ADR is about. `tsrs` owns types and the language service, Oxlint owns the Effect rules, and `effecttsgo/*` still resolves through the patched `oxlint-tsgolint` — verified, not assumed: an `Effect.gen` containing `new Date()` still reports `effecttsgo(global-date-in-effect)` as an error after the bump.

The `0.59.0` → `0.64.1` bump is the first one since the swap where the presets moved, and it moved them in both directions. The train ceiling did not: `0.64.1` supports tsrs `0.20.1-ts7.1.0-beta`, Oxlint `1.88`–`1.90` and `oxlint-tsgolint` `7.0.2004`/`7.0.2005`, so the compiler moved one patch (`0.20.0` → `0.20.1`), Oxlint moved one minor (`1.89.0` → `1.90.0`, with `@oxlint/plugins` tracking it), and `oxlint-tsgolint` stayed. tsrs `0.21.0` and Oxlint `1.91.0` both exist and both are refused by every released `@effect/tsgo`, which is the train working as designed: the compiler does not move until the language service names it.

Diffing the presets against `0.59.0`'s showed sixteen additions, one removal and no severity changes. The removal is `prefer-schema-over-json`, which this config had `error` everywhere and `off` for test files; it is replaced by `global-json` and `global-json-in-effect`, the same pair the `global-date`/`global-timers`/`process-env` boundary already uses. So `global-json` joins the four "legitimate outside Effect" `off` entries — a `JSON.parse` in a Vite config, the embeddable widget, the SDK, or a Drizzle JSON column is ordinary work — and `global-json-in-effect` is `error`, with the `prefer-schema-over-json` test exception carried over verbatim to its `-in-effect` sibling, since a test that builds the exact wire bytes a provider signs is testing the input, not a decode boundary. All nineteen `global-json-in-effect` findings were in test files and none in production code, so nothing had to change to make that entry stick.

Where the additions landed matters less than what they found. `global-json` and `global-json-in-effect` arrived in `effect-native`; `effect-try-without-catch` arrived in `antipattern`, which this config does not extend, and still reported — the plugin enables it at `warn` on its own, so a preset listing is not the list of rules that run. The other thirteen (`effect-succeed-with-undefined`, `fail-cause-to-constructor`, `flat-map-identity-to-flatten`, `manual-metric-tap-to-track`, `map-const-to-as`, `map-map-error-to-map-both`, `map-some-catch-no-such-element`, `match-boolean-to-is-success`, `provide-merge-all-to-array`, `result-match-to-from-result`, `suspend-fail-to-fail-sync`, `type-union-to-schema-union`, `yield-in-call-argument`) are stylistic swaps and report zero findings here, which is worth knowing before the next bump: they were the bulk of the two thousand findings the `0.47` bump produced, and their absence this time is a property of the tree, not of the presets.

Only `effect-try-without-catch` had findings worth acting on: ten sites where `Effect.tryPromise` had no `catch` handler and so produced the generic `UnknownError`. Those are fixed rather than silenced — a `catch` that names the domain error where the failure is meant to be handled (`seed.ts`'s sign-up, which now fails with `SeedDataError`) and `Effect.promise` where the rejection was already an all-outcomes-swallowed defect (`legid`'s `verify`/`parse`, `jwtVerify`'s per-secret loop, and the test helpers).

One finding from the same release window was not a lint problem at all but surfaced through the gate. Effect `4.1.2` gave `RateLimiter.layerStoreMemory` a janitor fiber on `Schedule.spaced("1 minute")`, and `TestClock.setTime` wakes each due sleep one at a time and waits for the woken fiber to suspend again — so every domain test that pinning the clock to a real date (the SSO and public-API suites) pumped the janitor roughly 29 million times and never returned. The `RateLimiter` here lives behind `RateLimitService.layerMemory`, so the fix belongs there: the store is built in a scope that closes immediately, which keeps the store value and drops the fiber. The store recomputes an entry's window on read, so an expired entry behaves like a missing one without the sweep, and nothing a test observes changed.

The `0.64.1` → `0.67.3` bump moved the train off the ceiling that the previous paragraph described. `0.67.3` supports tsrs `0.21.0-ts7.1.0-beta`, Oxlint `1.88`–`1.91.0` and `oxlint-tsgolint` `7.0.2004`/`7.0.2005`, so tsrs moved one minor (`0.20.1` → `0.21.0`), Oxlint moved one minor (`1.90.0` → `1.91.0`, `@oxlint/plugins` with it), and `oxlint-tsgolint` stayed at `7.0.2005`. Both halves of the old ceiling are still real, which is the distinction worth keeping: `7.0.2006`, tsrs `0.22.0` and Oxlint `1.92.0` are all published, the first two are listed by `@effect/tsgo@0.67.4` and the third by nothing, so a bump that reaches for any of them today fails `prepare` rather than moving the train.

That `0.67.3` lists a different matrix than its own published README is the practical lesson. `npm view @effect/tsgo@0.67.3 readme` serves the README of the newest publish, which already names tsrs `0.22.0` and `oxlint-tsgolint` `7.0.2006`; `prepare` then refuses both, which is how the ceiling was found. The authoritative matrix ships inside the release — `node_modules/@effect/tsgo/dist/effect-tsgo.cjs` carries the accepted versions for the installed build — so read it there before pinning, not from the registry's copy of the README.

Diffing the presets against `0.64.1`'s showed one addition and no removal or severity change: `recommended` gains `effecttsgo/match-to-result-or-option` at `warn`, and `effect-native` is byte-identical. It reports zero findings here, so there was no decision to record in `oxlint.config.ts` — the rule stays where the preset put it. The compiler half was as quiet: tsrs `0.21.0` ports the same TypeScript `7.1.0-beta` as `0.20.1`, so no package's types moved and the bump's only source edits were the ones the formatter made on its own version bump.

`0.67.3` → `0.67.4` is the shortest step the train has taken, and it is the one that clears the last ceiling. `0.67.4` lists tsrs `0.22.0-ts7.1.0-beta` and `oxlint-tsgolint` `7.0.2006` — both already older than the release gate — so only `@effect/tsgo` itself needed an exemption, and `minimumReleaseAgeExclude` names that one version rather than the three. The presets are byte-identical between the two releases and so is the Oxlint schema, so no rule arrived, none left, and no severity had to be decided. tsrs `0.22.0` ports the same TypeScript `7.1.0-beta` as `0.21.0`, and no package's types moved. The only new finding in the batch was not Effect's: `typescript/unbound-method` reported `fetch: handler.fetch` in `apps/web/server.mjs`, which the static-server work had just touched, and calling it as a method fixed it.

`0.67.4` → `0.70.0` is the first bump where the reason was a capability rather than a ceiling. `0.70.0` adds `--tsrs-lint`, which runs Oxlint's type-aware pass on the Effect-patched `tsrs` instead of on the Effect-patched `oxlint-tsgolint` — one TypeScript engine for the compiler and the linter, which is what `tsrs` was built for. It also names the newest published release of every component in the train, so the move is the whole way: tsrs `0.22.0` → `0.25.0`, Oxlint `1.91.0` → `1.94.0` with `@oxlint/plugins` tracking it, and `oxlint-tsgolint` retired rather than bumped (see the last paragraph). Every one of those was published more than a day before the bump, so `minimumReleaseAgeExclude` is empty and the entry it carried for `@effect/tsgo@0.67.4` is gone; the block is described in `pnpm-workspace.yaml` rather than left as an empty key.

The ceiling that had held Oxlint at `1.91.0` is gone rather than moved. `1.92.0`–`1.94.0` are all inside `0.70.0`'s range, so the type-aware pass is now on the newest published Oxlint, and the next step is again whatever `@effect/tsgo` lists next.

The presets moved by two rules, both `warn` in `recommended` and both addition: `flat-map-provide-service-to-provide-service-effect` and `on-exit-failure-to-on-error`. `effect-native` is byte-identical, and the Oxlint schema only gained definitions: `typescript/no-misused-promises`'s `checksConditionals` option widened from a boolean to a boolean-or-object, which is Oxlint's change between `1.91` and `1.94`, and nothing in `oxlint.config.ts` sets it. Both findings were the first rule, in `packages/domain/src/session-middleware.ts`, and both were fixed rather than left to the warning: `Effect.flatMap(session => effect.pipe(Effect.provideService(...)))` is what `Effect.provideServiceEffect` exists for, so the two middleware layers now forward the acquisition effect directly and the pipe that collapsed into it is gone. `on-exit-failure-to-on-error` reports nothing here.

Compilers were the quiet half again. tsrs `0.25.0` ports the same TypeScript `7.1.0-beta` as `0.22.0`, and no package's types moved — but the one place that records a compiler seam was re-tested rather than assumed. `packages/domain/src/email-subscription/repository.ts` reads a full row instead of projecting columns because a projection collapsed inference across the handler layer to `unknown` at three call sites under `0.22.0`; the same projection still collapses under `0.25.0`, so the full-row read stays and its comment now records the re-test instead of promising one.

The capability is the gate in the same change, because the gate was the only thing worth moving it for. `pnpm lint` and `pnpm lint:fix` are now `effect-tsgo --tsrs-lint oxlint`, and `oxlint-tsgolint` is no longer a dependency: the type-aware pass runs on the `tsrs` the `typecheck` task already uses, so the repo builds one TypeScript program per run instead of two and carries one fewer Go binary and its platform packages.

The swap was checked rather than assumed, on a clean tree with both engines installed. They produced **identical output**: 419 diagnostics over 1,864 files across 311 rules, with zero difference in rule, file, position, message or severity. The typed half was confirmed live rather than inferred from a clean run — a planted floating promise reports `typescript/no-floating-promises` under both — and the Effect half the same way, with `effecttsgo(global-date-in-effect)` an error under both. `--fix` and `--fix-suggestions` reach Oxlint unchanged (`--fix-suggestions` rewrote a probe file), and a run with an error-level finding exits `1`, so CI still fails on a finding. Warm wall time is ~10s either way, so nothing about the gate got slower.

What did change is where the patch lives. `effect-tsgo patch --oxlint` patches Oxlint and `oxlint-tsgolint` as one unit and fails if the tsgolint binary is missing, so dropping the dependency meant dropping that patch too: `prepare` now patches only `tsrs`, and the patched Oxlint binding is preloaded by the wrapper on each run. The consequence to know is that a bare `oxlint` reports the plain rules and no `effecttsgo/*` — there is no script that runs it that way, and `pnpm check` is the gate — while `effect-tsgo --tsrs-lint oxlint` validates the installed Oxlint against the versions the installed `@effect/tsgo` names before it lints anything. The version contract did not weaken; it moved from install time to lint time, which is where a mismatch now fails loudly.
