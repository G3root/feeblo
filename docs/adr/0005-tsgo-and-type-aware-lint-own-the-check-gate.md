# ADR 0005: TypeScript 7 and type-aware Oxlint own the check gate

## Decision

The workspace compiles with TypeScript `7.0.2` and lints with Oxlint `1.89.0` in type-aware mode. `@effect/tsgo@0.56.0` patches both tools in `prepare`, and Oxlint — not `tsc` — is the only surface that reports Effect diagnostics: `packages/config/tsconfig.base.json` sets `diagnostics: false` on the language-service plugin and `oxlint.config.ts` extends `@effect/tsgo/oxlint-presets/recommended` and `.../effect-native`. Every package declares `typecheck: tsc --noEmit`, and `pnpm check` (`turbo run check`) runs those together with the type-aware lint pass and the formatter check. CI runs it as the `checks` job.

## Why

Nothing typechecked the workspace. There was no `typecheck` script in any package, no `typecheck` task in `turbo.json`, and no lint or typecheck step in CI: `apps/web` builds through Vite, `apps/server` through Rolldown, and neither reads types. `packages/domain` compounded this by declaring `composite`, `declaration`, and `outDir` with nothing to emit them, so its `exports` map pointed at source while a latent `TS7056` sat in `rpc-router.ts` waiting for the first tool that asked tsc to serialize a declaration. TypeScript was an editor feature, not a gate.

Turning it on is cheap now. All 26 packages typecheck clean under TypeScript 7, and the first run surfaced exactly three real problems: the `TS7056` above and two tsconfigs (`packages/sdk`, `packages/feedback-widget`) that declared `outDir`/`declaration` without `rootDir`. That is the whole migration.

Type-aware linting had been disabled deliberately — the config carried "revisit once Oxlint's tsgolint path can integrate with `@effect/tsgo` diagnostics" next to `typeAware: false`. That integration is what `@effect/tsgo` now is: the patch wires the `effecttsgo` plugin into Oxlint, and `oxlint-tsgolint` provides the type information. The cost of the old setting was 17 `typescript/*` rules switched off, including `no-floating-promises`, which is the highest-value rule in an async codebase.

Splitting responsibility between the two tools keeps each one honest. `tsc` owns types and stays fast enough to cache per package; Oxlint owns Effect rules, where per-rule severity, file-scoped overrides, and a single cached run are easier to reason about than a tsconfig severity map. Running the Effect rules in both places would report every finding twice.

## Consequences

Every Effect rule now lives in `oxlint.config.ts`, and changing a diagnostic severity is a config edit rather than a tsconfig edit. The `effecttsgo` rules that fire on usage anywhere in a file — `async-function`, `global-date`, `process-env`, `global-console` — are `off` with written reasons, because this repo deliberately keeps those behaviors outside Effect at its boundaries (Playwright specs, TanStack Start server functions, better-auth plugins, the standalone widget, Node scripts). Their `-in-effect` siblings stay on, and those are the ones that describe a defect.

`oxlint.config.ts` extends two `@effect/tsgo` presets, `recommended` and `effect-native`, and the second is not optional. `@effect/tsgo@0.46` moved twenty rules — every `global-*`, `crypto-*`, `process-env`, `new-promise`, `schema-sync` and `instance-of-schema` — out of `recommended` and into the opt-in `effect-native` preset. Extending only `recommended` therefore drops `global-date-in-effect`, the rule the paragraph below is about, without failing anything: the diagnostic simply stops being reported. The two presets together are exactly the rule set `0.45.0`'s `recommended` carried. A tsgo bump is not safe to review by watching `pnpm check` go green; it has to be reviewed by diffing the presets.

That distinction is the thing to know when reading the warning count. The bare variants fire in files with no Effect context at all, so their totals overstate the problem badly: `new-promise` (21) is Storybook mocks, a framework-agnostic editor, and Playwright specs; `global-timers` (12) is Storybook, the embeddable SDK, a PostHog provider, and a clipboard hook; `schema-sync` (39) is entirely `decodeUnknownSync` in test files, where a throw is what you want; `any-unknown-in-error-context` (517) is 431 test files plus HTTP router plumbing where the `unknown` is inference, not a decision. None of those should be churned to satisfy a rule whose advice does not apply. What is genuinely actionable, in order:

1. `global-date-in-effect` — cleared outside `packages/db/seed.ts`, and flipped from `warn` to `error` with a file-scoped `warn` override for that script. The rule ranked first because `new Date()` inside Effect bypasses `Clock`, so a service that does it cannot be tested against `TestClock`. The runtime services read `Clock`/`DateTime`, and the fixtures that constructed a `Date` inside Effect were converted: dynamic reads go through `DateTime.nowAsDate` or `Clock.currentTimeMillis`, and fixed instants go through a local `dateAt` helper that builds the `Date` with `DateTime`. The 22 left are the seed script's snapshot timestamps; that script is a human-facing CLI, so deciding them is separate work rather than a mechanical sweep.
2. `typescript/no-floating-promises` (49, 45 of them production, mostly React event handlers) — a floating promise in a handler is an unhandled rejection.
3. `strict-effect-provide` (31) and `any-unknown-in-error-context` (the 86 production sites) — both now `error` and clear. The second cleared itself once the `effect` bump was actually read: the 154 findings that survived the tsgo upgrade were every one of them downstream of a single breakage — Effect `4.0.5` turned `Crypto.randomUUIDv4`/`randomUUIDv7` from properties into methods, so `crypto.randomUUIDv4.pipe(...)` became `.pipe` on a function, the whole Effect became `unknown` in both channels, and the diagnostic followed that `unknown` outward to every repository and handler that consumed one. Twelve call sites gained their parentheses and 154 warnings went with them. That is the rule working as intended, and it is why the count is worth reading rather than estimating.
4. `global-console-in-effect` (26) is 24/26 in `packages/db/seed.ts`, a human-facing CLI where `console.log` prints the output an operator expects; `Effect.log` would add fiber and timestamp noise. Leave it unless that script becomes machine-read.

Each should be fixed and then flipped to `error`. None should be silenced.

One rule is `off` for a reason that is neither "the code does this legitimately" nor "the advice does not apply": `unstable-api-usage`, which `@effect/tsgo@0.47` enables by default and which reports 928 findings here. Effect 4.0 moved `http`, `http-api`, `rpc`, `sql`, `persistence`, `reactivity` and `workflow` from `effect/unstable/*` to `effect/*` while keeping every one of them tagged `@stability unstable`, so the rule fires on the imports this server is built out of and there is nothing stable to migrate to. The warning is a true statement about the dependency and not about this code, and the control for it is the catalog pin, which is what decides when those APIs move. Leaving 928 of them as warnings would only train reviewers to skim the report, so the rule is off rather than ratcheted.

Tests keep one documented exception to the manual-runtime ban: `packages/auth/src/api-key.test.ts` builds `ManagedRuntime` values at module scope, because it shares one PGlite database across the file and passes it to the better-auth adapter as a plain value rather than inside an Effect. Its `oxlint-disable` carries the reason inline. Every other test file uses `it.effect`/`it.layer`, enforced by `tools/oxlint/effect-tests`.

`extends-native-error` stays on as a warning rather than being fixed: `RpcError` in `packages/web-shared` and `EmbedError` in `packages/sdk` are deliberately plain `Error` subclasses that never enter an Effect failure channel, and the SDK one must not pull `effect/Schema` into the embeddable bundle.

A dependency bump now has a version contract. `@effect/tsgo` names the TypeScript, Oxlint, and `oxlint-tsgolint` versions it supports; `effect-tsgo patch` validates them and refuses to patch a mismatch, so these four pins move together or not at all. It is also coupled to `effect` itself, which the patch command cannot check: the rules match on Effect's module paths, so `@effect/tsgo@0.45` keyed off `effect/unstable/*` reports nothing once Effect 4.0 drops the `unstable` segment. That failure is silent, so a tsgo bump is reviewed by diffing its presets against the ones the config extends, not by watching the gate.

The `0.47.2` → `0.56.0` bump is the first to exercise that contract concretely, and it dragged the other three pins with it: `0.56.0` supports TypeScript `7.0.2`, Oxlint `1.87`–`1.89` and `oxlint-tsgolint` `7.0.2003`/`7.0.2004`, so Oxlint and `@oxlint/plugins` moved to `1.89.0` and `oxlint-tsgolint` to `7.0.2004`, because those were the only installable versions left. Diffing the presets showed ten additions, no removals and no severity changes: seven in `recommended` (`effect-sleep-zero-to-yield-now`, `error-payload-shadows-name`, `experimental-api-usage`, `flat-map-to-tap`, `schema-class-missing-brand`, `schema-class-object-literal`, `unstable-api-usage`) and three in `effect-native` (`prefer-effect-array`, `prefer-effect-record`, `prefer-effect-string`). `unstable-api-usage` arriving in `recommended` is already covered by the `off` entry above; the rest were decided one at a time, with the reasoning beside their entries in `oxlint.config.ts`. Two account for 2,641 of the 2,651 new findings — the `prefer-effect-*` trio (2,514) and `schema-class-missing-brand` (127) — and both are `off` rather than ratcheted. The first is a stylistic swap to a module whose functions behave identically, at roughly a thousand sites that sit in browser bundles, Playwright specs and the published SDK, where the import is bundle weight and the behaviour is unchanged; the second fires only on `Schema.TaggedError`, whose required unique `_tag` already rejects two structurally identical errors, so the brand would be a symbol nothing matches on. `typescript/no-generated-empty-object-type` reports two findings, both a deliberate `Schema.Struct({})` that states "nothing to configure", and is `error` everywhere except those two named files.

The bump also showed what a green gate does _not_ prove. `typecheck` is cached, and the cache did not include the resolved dependency versions: appending a line to `pnpm-lock.yaml` left every package replaying `cache hit`, so after a real dependency bump a package whose types no longer compiled could report success from a run that predates the install. That is the hazard the `//#toolchain` and `//#knip` tasks document for themselves and dodge by not caching at all; `typecheck` is worth caching, so `turbo.json` names `pnpm-lock.yaml` as a `globalDependencies` entry instead — one miss per dependency change, and the cache still works for source-only edits. Two consequences for anyone bumping a train: read the result of `pnpm check --force` once, and treat a per-package `typecheck: cache hit` after an install as no evidence.
