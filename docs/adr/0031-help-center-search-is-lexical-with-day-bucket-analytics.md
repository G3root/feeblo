# ADR 0031: Help-center search is lexical-first, and its analytics are day buckets

## Decision

Four choices, all additive to ADR 0029:

- **Lexical first, semantic as a rescue.** `help_center_article.search_vector` is a generated `tsvector` (`title` weight `A`, `excerpt` `B`, `content` `C`, `english` configuration), indexed with GIN, ranked by `ts_rank_cd`. Articles also carry an embedding, and the semantic pass runs **only when the lexical pass returns fewer than three pages**; its hits are appended behind the lexical ones.
- **The query is built by one module and nothing else may produce it.** `help-center-article/search.ts` normalizes the text, keeps letters and digits, drops one-character terms and duplicates, caps the term count, and emits prefix branches. The repository binds that string and never a caller's.
- **A write schedules its own embedding, detached and best-effort.** The embedding columns are an index, not content: a model that is unreachable logs and leaves them null, and the save still succeeds.
- **Search and article traffic are counted in day buckets, written on the read path, and advisory.** `help_center_search_daily` and `help_center_article_daily` are keyed by `(organization, day, …)` and `(article, day)`; a failed counter write is logged and ignored, and never fails the read that produced it.

## Why

**Why a generated column.** The three inputs are columns on the same row, so Postgres can always compute the vector and no caller can forget to. A trigger has to be replayed by restores and bulk inserts and can silently miss a path; a write-path update is one more statement every future write has to remember. `to_tsvector('english'::regconfig, …)` is immutable because the configuration is a literal, which is what makes the column admissible at DDL time — a parameterized config is rejected by Postgres, and that constraint is the one thing to know before changing the expression. The cost is a second copy of the body in vector form; a vector is far smaller than the Markdown it indexes.

**Why lexical first.** Lexical search is deterministic, explainable — an editor can see why a page ranked — costs nothing per query, and works in PGlite, which is what the tests run on. It is also the answer to the common query, which is a word the page actually contains.

**Why the semantic pass is a rescue and not a ranker.** Two reasons, and neither is a preference. _Cost_: the search box is public and unauthenticated, so embedding every query would put a metered model call on a keystroke; rescuing only a thin result set spends it on the searches that were about to fail. _Ranking_: `ts_rank_cd` is unbounded and depends on the query's term count, cosine distance is bounded and model-specific, and any arithmetic combining them would be a constant nobody could defend with evidence. Exact-word evidence keeps its precedence, near-miss evidence fills the tail, and a learned ranker is a later decision with data behind it. Three is the threshold because it is the number of results a reader scans before deciding the page is useless: above it the append adds noise to a page that already answered, below it the search looks broken.

**Why the embedding is written on save rather than backfilled.** The three inputs are on the row and the write paths are the only places an article changes, so a save can schedule the refresh and a detached job can do it. A backfill sweep would need its own runner, its own progress records and its own outage handling for a table whose unembedded rows degrade to "lexical only" — which is the shipped behaviour, not a broken state. The cost is stated rather than hidden: an article written before this shipped has no vector until it is next saved, and switching `EMBEDDING_MODEL` strands the old rows because the semantic query filters on the model.

**Why `strict` disables the semantic pass.** A strict search exists for the widget's deflection, whose whole purpose is to show a page that shares the visitor's words. A semantic neighbour with no word overlap is exactly the suggestion that looks like a mistake beside a feedback form. Disabling it there also means a deployment with no embedding key still answers the deflection.

**Why prefix branches and not `websearch_to_tsquery`.** `websearch_to_tsquery` tolerates arbitrary input but has no prefix operator, so it cannot answer a search box: a reader who has typed "export" would see nothing until the word is complete. `to_tsquery` does have `:*`, and it throws on malformed input — which is why the tokenizer is the only producer of the string. Everything that `to_tsquery` treats as syntax (`&`, `|`, `!`, parentheses, `:`, `'`) is a separator before it is an operator, so a reader's punctuation cannot reach the parser. Precision is the ranking's job: `ts_rank_cd` rewards coverage over a single mention, and the weights put a title match above a body match.

**Why the same query serves both surfaces with a flag.** The dashboard must find a draft its editor is writing; the portal must never reveal one. Making the readable-state filter a **parameter of the repository call** rather than something each caller remembers is the difference between a search box and a leak, and it mirrors how every other public read is scoped.

**Why advisory writes.** Analytics is not the product. A search that returns results and fails to count them is a working error; a search that fails because a counter could not be written is a broken one. The same reasoning applies to a verdict: the vote lands first, and its bucket is best-effort. Wrapping the read and its counter in one transaction would take a write lock on a read path, which is a worse trade than a lost count.

**Why day buckets rather than raw events.** The questions are bounded — "which articles lately", "what do readers search for", "what do they search for and not find" — and a bucket answers each with one grouped query. Raw search events would be a text log with a retention problem and a privacy surface (a reader's search terms attached to a timestamp), and the first thing anyone would build on top of them is this table. A bucket is its own natural key, so there is no surrogate id to write the same fact twice under.

**Why verdict buckets count verdicts cast.** A flip is a second judgment, not a correction of the first, and crediting today's bucket with the flip while leaving the earlier day intact is what makes the daily series mean "how readers judged pages this week". The standing distribution — the number on the article — is the feedback table's own `count(*)`, which is exact because those rows are never pruned. Storing a second, slower-moving copy of it here would create two numbers that disagree.

## Consequences

- **Search is English-stemmed for every workspace.** The text-search configuration is part of the index, so per-locale or per-workspace configurations are a different column and a different decision; a non-English help center searches by exact words with English stopwords dropped.
- **`help_center_search_daily` is the first table here that would need retention**, because its key includes the reader's text. Growth is bounded by distinct queries per workspace per day, which is human-entered text; if that assumption stops holding, a prune by `day` is the fix and the aggregates it feeds are already windowed.
- **The widget's deflection is public, unauthenticated and plan-free.** It answers `{ articles, enabled }` — `enabled: false` for a deployment with the flag off or a workspace with no public help center — because a distinguishable failure would confirm which workspaces exist. It is on every plan: the ceiling on articles already prices the feature, and a deflection that only some plans get would be a worse help center rather than a smaller one.
- **One portal-URL builder.** `site/url.ts` owns `<custom domain>` or `<subdomain>.<root>`, and both the email outbox and the widget's article links go through it, because the widget iframe is embedded on the customer's own origin and a relative link would resolve against the host page.
- **The semantic half costs a model call per rescued search.** It is bounded by the thin-result rule, the public rate limiter, the 120-character query cap, and `strict` refusing to embed at all; a deployment with no `EMBEDDING_API_KEY` never runs it.
- **An article's body is truncated to 6,000 characters for its embedding.** The head of a page is what identifies it, and an unbounded body is an unbounded provider cost per save.
- **ADR 0029's "no `tsvector` anywhere in this codebase" and "the embedding columns ship unused" no longer hold.** This ADR adds the lexical index beside the vector one, and a writer for the vector.
